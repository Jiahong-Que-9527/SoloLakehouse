# SoloLakehouse v2.6 — 演示目标：可执行的治理证据

**状态**：v2.6 目标定义
**受众**：招聘经理、数据/平台工程师、金融与合规利益相关者、航空物流数据团队
**版本边界**：v2.6 是治理证据版本；不是 Kubernetes、多引擎、通用可观测性或 Agent UI 版本。

## 一句话目标

> 当监管者、审计师或业务负责人询问一张关键数据从哪里来、谁负责、经过什么转换、能否相信时，SoloLakehouse 能在一分钟内产出可归档、可验证的证据包。

这证明的是 **compliance evidence as an executable platform capability**，而不是一份政策文档、一个仪表盘宣称或法律意义上的合规认证。

## 要展示的能力

| 能力 | 对外可见的证明 |
| --- | --- |
| 数据契约即代码 | 关键数据集的 owner、business purpose、classification、refresh SLA、retention、consumer 与 access policy 是可机读、可校验的契约字段。 |
| 质量门禁 | 关键数据不满足 freshness、shape 或约定质量条件时，系统明确阻止或标记风险。 |
| 三源血缘融合 | OpenMetadata 的责任/治理元数据、Iceberg snapshot 的数据版本、Dagster run 的编排上下文被关联到同一个 `LineageRecord`。 |
| 一键证据响应 | `make lineage-evidence DATASET=... DATE=...` 生成稳定命名的 manifest 和证据包。 |
| Fail loudly | 关键来源字段缺失时，系统拒绝生成看似完整的证据；不得静默产生部分或误导性输出。 |
| 证据归档 | 如果 Object Lock/WORM 实现并验证，已归档证据不能被静默覆盖或删除。未验证前，不得作此宣称。 |

## 5 分钟演示路径

### 场景开场（30 秒）

> 一项受监管的金融指标受到质疑。团队需要在 24 小时内说明它的数据来源、版本、转换过程、运行上下文和责任人。

本演示聚焦数据集：`fin.ecb_dax_features_gold`。

### 1. 展示数据契约（45 秒）

打开该数据集及其关键上游的契约，说明：

- 谁拥有该数据集；
- 它服务什么业务目的；
- 分类、保留期与允许消费者；
- 刷新 SLA 和质量等级。

**话术**：治理不是散落在 README 里的描述；它是可执行、可被验证的系统输入。

### 2. 展示治理门禁（45 秒）

在受控 demo fixture 中移除一个必填治理字段，运行契约校验，展示明确失败。

**话术**：缺少责任、用途或关键政策信息时，平台不允许把数据集伪装成受治理资产。

### 3. 生成运行与血缘上下文（45 秒）

执行或展示一次完整数据流：

- Dagster 产生 run 与资产上下文；
- Iceberg 产生可引用 snapshot；
- OpenMetadata 提供责任与治理元数据。

不以服务数量为重点；重点是三类独立事实如何形成可验证的共同记录。

### 4. 一键生成证据（60 秒）

执行：

```bash
make lineage-evidence DATASET=fin.ecb_dax_features_gold DATE=<ISO-date>
```

展示命令在目标时间内完成，并输出稳定路径下的 evidence bundle 与 manifest。

### 5. 打开生成物（60 秒）

展示证据包中的：

- dataset ID、owner、业务目的与治理分类；
- Iceberg snapshot ID、提交时间与数据版本；
- Dagster run、触发信息与转换上下文；
- 上游/下游关系、质量状态；
- manifest、生成时间和归档位置。

### 6. 证明系统不会伪造可信度（30 秒）

在受控 fixture 中让一个必需来源缺失，展示 CLI fail-fast，并指出缺失的具体事实。若 WORM 已经真实验证，再展示归档证据无法被静默覆盖或删除。

**收尾话术**：系统宁愿清楚地报告“证据不完整”，也不生成误导审计判断的输出。

## 受众叙事

| 受众 | 应强调什么 |
| --- | --- |
| 招聘经理 | 从“平台能跑”推进到“平台能解释、能审计、能承担责任”。 |
| 金融/合规角色 | 面对数据影响范围或监管问询，可快速获得结构化证据，而非人工拼接截图。 |
| 航空物流角色 | 同一治理能力可用于关键运营数据的责任、质量、谱系与事件追溯。 |
| 技术同行 | 治理元数据可执行；三个独立系统的信号被统一；缺失证据 fail-fast。 |

## 发布展示包

v2.6 不以代码合并即完成。对外展示前必须准备：

- [ ] 一张“监管问题 → 三源融合 → 证据包”的架构图；
- [ ] 可稳定运行的 5 分钟 live demo；
- [ ] 90 秒录屏，适合 LinkedIn 与初次外联；
- [ ] 一份脱敏、由真实运行生成的 evidence bundle；
- [ ] 一次 regulator-response drill 报告，含耗时、产物与限制；
- [ ] 一页 case study：问题、设计选择、结果、限制与明确不做什么；
- [ ] 对所有合规与不可变性主张的验证记录；未验证的能力必须标记为限制，不得暗示已具备。

## v2.6 演示验收标准

演示目标达成的最低条件：

1. `make lineage-evidence` 对至少一个关键 Gold 数据集可端到端成功；
2. 结果包含三源血缘、治理契约与可归档 manifest；
3. 缺失关键来源时可重复地 fail-fast；
4. 一次演练记录从请求到证据包的真实耗时；
5. 演示者能在五分钟内讲清业务问题、技术取舍、结果与限制；
6. 任何“DORA-ready”或“immutable/WORM”表述均有对应的实现与验证证据。

## 不做什么

- 不从容器数量、工具数量或 dashboard 数量开始演示；
- 不把 reference implementation 表述为客户已经合规或获得监管认证；
- 不隐藏失败、缺失来源或未完成的安全能力；
- 不为展示效果引入与证据闭环无关的新运行时服务。
