# SoloLakehouse v2.6 — Demo Goal: Executable Governance Evidence

**Status**: v2.6 goal definition
**Applies to**: governance, audit, and regulatory-enquiry response on a regulated data platform
**Version boundary**: v2.6 is the governance-evidence version. It is not a Kubernetes, multi-engine, general-observability, or agent-UI version.

## Goal in one sentence

> When a regulator, an auditor, or a business owner asks where a critical dataset came from, who is responsible for it, what transformed it, and whether it can be trusted, SoloLakehouse produces an archivable, verifiable evidence bundle in under a minute.

What this demonstrates is **compliance evidence as an executable platform capability** — not a policy document, not a dashboard claim, and not a legal compliance certification.

## Capabilities on display

| Capability | Externally visible proof |
| --- | --- |
| Data contracts as code | Owner, business purpose, classification, refresh SLA, retention, consumers, and access policy are machine-readable, validated contract fields for every critical dataset. |
| Quality gates | When critical data fails freshness, shape, or agreed quality conditions, the system blocks it or flags the risk explicitly. |
| Three-source lineage join | OpenMetadata's ownership/governance metadata, the Iceberg snapshot's data version, and the Dagster run's orchestration context are joined into a single `LineageRecord`. |
| One-command evidence response | `make lineage-evidence DATASET_ID=... DAGSTER_RUN_ID=...` produces a stably named manifest and evidence bundle. |
| Fail loudly | When a required source field is missing, the system refuses to produce evidence that would look complete. No partial or misleading output. |
| Evidence archival | Once Object Lock/WORM is implemented and verified, archived evidence cannot be silently overwritten or deleted. Until verified, this claim must not be made. |

## Five-minute demo path

### Opening the scenario (30s)

> A regulated financial metric has been challenged. The team must explain its data sources, version, transformations, run context, and accountable owner within 24 hours.

This demo focuses on one dataset: `fin.ecb_dax_features_gold`.

### 1. Show the data contracts (45s)

Open the contract for the dataset and its critical upstreams, and explain:

- who owns the dataset
- what business purpose it serves
- its classification, retention period, and permitted consumers
- its refresh SLA and quality class

**Talking point**: governance is not prose scattered across a README; it is an executable, verifiable system input.

### 2. Show the governance gate (45s)

In a controlled demo fixture, remove one required governance field, run contract validation, and show it fail explicitly.

**Talking point**: without accountability, purpose, or key policy information, the platform will not let a dataset pose as a governed asset.

### 3. Produce run and lineage context (45s)

Execute or show one complete data flow:

- Dagster produces the run and asset context
- Iceberg produces a referenceable snapshot
- OpenMetadata supplies ownership and governance metadata

The point is not how many services are running. The point is how three independent facts form one verifiable joint record.

### 4. Generate evidence with one command (60s)

```bash
make lineage-evidence \
  DATASET_ID=fin.ecb_dax_features_gold \
  DAGSTER_RUN_ID=<successful-dagster-run-id>
```

Show the command completing within the target time and writing an evidence bundle and manifest to a stable path.

### 5. Open the artifact (60s)

Show what the evidence bundle contains:

- dataset ID, owner, business purpose, and governance classification
- Iceberg snapshot ID, commit time, and data version
- Dagster run, trigger information, and transformation context
- upstream/downstream relationships and quality status
- the manifest, its generation time, and its archive location

### 6. Prove the system will not fake trustworthiness (30s)

In a controlled fixture, make one required source unavailable. Show the CLI fail fast and name the specific missing fact. If WORM has been genuinely verified, also show that archived evidence cannot be silently overwritten or deleted.

**Closing talking point**: the system would rather report "the evidence is incomplete" clearly than produce output that misleads an audit judgement.

## Narrative emphasis by role

| Role | What to emphasize |
| --- | --- |
| Data / compliance governance | Structured evidence on demand for data-impact or regulatory questions, instead of manually assembled screenshots. |
| Owner of critical operational data | The same governance capability applies to accountability, quality, lineage, and incident traceability for critical operational data. |
| Platform / data engineering peers | Governance metadata is executable; signals from three independent systems are unified; missing evidence fails fast. |
| Engineering leadership | Moving from "the platform runs" to "the platform can explain itself, be audited, and carry accountability". |

## Release presentation pack

v2.6 is not finished when the code merges. Before showing it externally, prepare:

- [ ] one architecture diagram: regulatory question → three-source join → evidence bundle
- [ ] a reliably repeatable five-minute live demo
- [ ] a 90-second screen recording suitable for a first outreach message
- [ ] one redacted evidence bundle produced by a real run
- [ ] a regulator-response drill report with elapsed time, artifacts, and limitations
- [ ] a one-page case study: problem, design choices, result, limitations, and what is explicitly out of scope
- [ ] verification records for every compliance and immutability claim; any unverified capability must be listed as a limitation and never implied as present

## v2.6 demo acceptance criteria

The minimum conditions for the demo goal to be met:

1. `make lineage-evidence` succeeds end to end for at least one critical Gold dataset
2. the result contains the three-source lineage, the governance contract, and an archivable manifest
3. a missing critical source fails fast, reproducibly
4. one drill records the real elapsed time from request to evidence bundle
5. the presenter can explain the business problem, the technical trade-offs, the result, and the limitations in five minutes
6. every "DORA-ready" or "immutable/WORM" statement is backed by a corresponding implementation and verification record

## What not to do

- do not open the demo with a count of containers, tools, or dashboards
- do not present a reference implementation as a customer already being compliant or regulator-certified
- do not hide failures, missing sources, or incomplete security capabilities
- do not introduce new runtime services unrelated to the evidence loop just for presentation effect
