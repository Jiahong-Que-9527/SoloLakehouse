# v2.6 Execution Plan

## Purpose

This document turns the v2.6 planning narrative into an execution sequence for
the repository.

Use it after reading:

- `docs/history/v2.6-planning.md`
- `TASKS.md`

## What v2.6 Actually Needs to Prove

v2.6 is successful only if the repository can answer this question with a real
command:

> For a governed Gold dataset, can the platform produce a structured,
> archivable lineage evidence bundle quickly and repeatably?

That means v2.6 is not mainly about dashboards, UI polish, or broader platform
expansion. It is about making governance evidence concrete.

## Scope

### In scope

- dataset contracts
- quality gates required by governed datasets
- three-source lineage join
- evidence CLI
- audit-path evidence output

### Out of scope

- multi-engine demos
- ML model cards
- SLO dashboards
- secrets rotation
- Kubernetes migration

## Design Sequence

The safest sequence is:

```text
dataset contracts
  -> lineage record schema
     -> source adapters
        -> three-source join
           -> evidence CLI
              -> audit output
                 -> drill and release gates
```

This order matters because the lineage join depends on stable dataset identity,
and the CLI depends on the join shape being stable first.

## Phase Breakdown

### Phase 1: Contracts and Validation

Goal:

- make governance metadata machine-readable

Deliverables:

- `governance/datasets/*.yaml`
- contract schema validation
- CI gate for contract completeness

Why first:

- `dataset_id` is the join key for v2.6
- owner/SLA/quality metadata should not be inferred ad hoc in the evidence CLI

### Phase 2: Evidence Data Model

Goal:

- define the evidence object before building the fetch logic

Deliverables:

- `LineageRecord`
- output manifest shape
- audit output directory conventions

Required fields should include at least:

- `dataset_id`
- `generated_at`
- `owner`
- `business_purpose`
- `quality_class`
- `refresh_sla`
- `openmetadata`
- `iceberg_snapshot`
- `dagster_run`
- `source_of_truth`

### Phase 3: Source Adapters

Goal:

- extract the required inputs from each evidence source independently

Adapters:

1. OpenMetadata adapter
2. Iceberg snapshot adapter
3. Dagster run adapter

Rule:

- each adapter should fail clearly on missing critical fields
- do not bury source failures inside a partial success artifact

### Phase 4: Join and CLI

Goal:

- turn structured inputs into an operator-facing command

Deliverables:

- join logic keyed by `dataset_id`
- `make lineage-evidence DATASET=... DATE=...`
- evidence bundle output

The first supported target should be one governed Gold dataset only.
Do not try to generalize to every dataset before the first path works.

### Phase 5: Hardening

Goal:

- make v2.6 releasable rather than merely implemented

Deliverables:

- tests
- one drill
- release/readiness doc updates
- known-limitation notes

## First Dataset Recommendation

Use the first governed Gold dataset as the initial v2.6 path:

- `fin.ecb_dax_features_gold`

Reason:

- it is the most visible governed output in the current platform narrative
- it already sits at the center of the existing demo and ML story
- it exercises all three evidence sources naturally

## Recommended Implementation Milestones

### M1

- contract schema exists
- first five contract files exist

### M2

- `LineageRecord` schema exists
- adapters return typed objects

### M3

- local evidence generation works for one target dataset

### M4

- `make lineage-evidence` exists
- audit output exists
- tests exist

### M5

- drill recorded
- release/readiness docs updated

## Risks to Avoid

### Risk 1: starting with the CLI

If the CLI comes before the schema and adapters, its output shape will churn and
tests will be unstable.

### Risk 2: making contracts optional

If owner/SLA/quality metadata can be omitted, the evidence pack becomes
narratively weak at exactly the point where v2.6 is supposed to be strongest.

### Risk 3: expanding v2.6 sideways

It is easy to let v2.6 absorb:

- more observability
- more release process
- ML governance
- portability work

That would dilute the milestone and delay the first usable evidence path.

## Current Recommendation

The repository should start with:

1. `TASKS.md` Block A
2. `TASKS.md` Block H
3. a small `Block G` documentation pass after the feature works

Everything else should wait.
