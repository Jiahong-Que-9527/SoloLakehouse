## 3. 下一步优先级排序

## P0：先完成 FinLakehouse 实体验收

这是当前最该做的事，也是所有后续版本演进的真实起点。

建议按以下顺序执行：

1. 按 `docs/finlakehouse-env-template.env` 生成实体 `.env`。
2. 按 `docs/vps-deployment-runbook.md` 在独立 VPS 上部署 `finlakehouse`。
3. 跑 `ENV_FILE=/opt/finlakehouse/.env make verify`。
4. 跑 `ENV_FILE=/opt/finlakehouse/.env make demo`。
5. 跑 `ENV_FILE=/opt/finlakehouse/.env make pipeline`。
6. 执行一次 FinLakehouse 自己的 Iceberg restore drill。
7. 把演练记录写入 `docs/restore-drills/YYYY-MM-DD-finlakehouse-iceberg-restore-drill.md`。

只有这一步完成后，项目才真正从“模板能力”进入“实体能力”。

## P1：收口文档与导航漂移

当前有一个小但真实的问题：仓库根目录实际存在的是 `task.md`，但多份文档仍在引用 `TASKS.md`。

这不会阻塞部署，但会带来两个坏处：

- 新接手者容易误判“任务板丢了”；
- 规划文档会显得与仓库当前结构不完全一致。

因此建议在不大改历史文档的前提下，优先修正常用导航文档。

## P2：再启动 v2.6

在 FinLakehouse 验收完成之前，不建议直接跳入 v2.6 实现。

原因很简单：

- `task.md` 明确要求不要把实体拆分、对象存储替换、治理升级混在一起做；
- 当前最缺的不是“新功能”，而是“当前能力已经在实体环境被证明”；
- 如果现在直接开 v2.6，会把风险源混在一起，后面很难判断问题来自模板、环境，还是治理新代码。

## 4. v2.6 启动时的推荐切入顺序

一旦 FinLakehouse 完成部署验收，v2.6 最合理的实现顺序建议是：

1. **数据契约先行**
   - 建 `governance/datasets/*.yaml`
   - 做 schema 校验
   - 让关键 Gold/Silver 数据集具备 owner、SLA、quality class、retention 等字段

2. **三源 lineage 融合**
   - OpenMetadata 元数据
   - Iceberg snapshot
   - Dagster run context

3. **证据导出命令**
   - 增加 `make lineage-evidence DATASET=... DATE=...`
   - 输出结构化 evidence pack

4. **audit bucket 落盘与 WORM**
   - 把 evidence 写到 `AUDIT_BUCKET`
   - 之后再补 object lock / 不可变策略验证

这个顺序的好处是：先把 join key 和契约立住，再做产物与归档，不会反复返工。
